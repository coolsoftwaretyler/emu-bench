# T11: Maestro E2E flow + flake-rate runner (Group 6)

**Status:** done (2026-09-03)
**Depends on:** T04 (rig), T06 (scroll/nav scenes as flow targets)
**Blocks:** T13

## Context

E2E duration and **flake rate** are the CI-relevant numbers (PLAN.md Group 6): CI throughput = duration × (1 + flake rate), so a fast-but-flaky environment loses to a slower reliable one. One flow, identical YAML on both platforms except launch stanzas.

## Scope

- `flows/e2e.yaml`: launch rig → fill a small form scene (add a `form.basic` scene to the rig if T04's debug screen doesn't suffice — keep it trivial: two inputs + a submit that navigates) → scroll a list (reuse `list.scroll` scene in manual-scroll mode: add a `mode=manual` param disabling auto-scroll so Maestro swipes) → navigate via `nav.transitions` screens → assert a terminal testID.
- Duration runner: n≥10 timed executions per platform, cold app start each time, device already booted (boot time is T10's metric, not this one).
- Flake runner: 50 executions per platform; classify each as pass / fail-flake (passes on immediate retry) / fail-real; emit duration samples + flake rate. Persist per-iteration logs for failed runs under `results/logs/` (gitignored).
- Registry entries `e2e.duration` and `e2e.flake_rate`, group 6.

## Acceptance criteria

- [x] The flow passes ≥ 48/50 on the simulator on this machine (if it doesn't, the flow itself is flaky — fix the flow, not the number; document any legitimate environment flake found on the way). Evidence: `./bin/emu-bench run --groups 6 --legs c --label e2e-flake50 --flake-runs 50` → `emu-bench: e2e.flake_rate leg c: 50/50 pass, 0/50 fail-flake (retry passed), 0/50 fail-real (retry also failed) -- flake rate 0.0%, real failure rate 0.0%`, written to `results/apple-m3-max-2026-09-03-e2e-flake50.json` (`e2e.flake_rate` row: leg c, n=48 post-warmup-discard, median 37.19s, cv 0.0106 — no unusually slow or wide-variance samples). Getting here required fixing two real, reproducible flow bugs found only by running genuine cold-start cycles repeatedly (not by inspection): (1) a fresh `am force-stop`-then-`launchApp` process start needs the JS bundle time to initialize before any deep link can land — Maestro's own `launchApp` "COMPLETED" fires as soon as the launch intent is issued, confirmed via maestro.log timestamps showing `Launch app ... COMPLETED` and the first `openLink` only ~1ms apart on a real failed run; both `openLink`s were then silently lost on 10/10 reproductions with no queuing or retry. Fixed by inserting `waitForAnimationToEnd: {timeout: 3500}` right after `launchApp` (tuned empirically: 2000ms passed only 9/10 in one batch, 3500ms passed 12/12 in a follow-up). (2) A genuine react-native-screens native crash ("Index 1 out of bounds for length 1" in `ScreenStackViewManager.getChildAt`/`SurfaceMountingManager.removeViewAt`, confirmed via the app's own red-screen and stack trace) when the flow's second `openLink` re-delivered a URL to the already-mounted `nav.transitions` scene mid-mount, racing its native screen-stack view manager — a real environment/library flake this ticket's own "document any legitimate flake found on the way" clause covers, not something a duration/flake-rate number can paper over. Fixed by keeping the double-`openLink` workaround only for the one genuine cold-launch step (`form.basic`, right after `launchApp`) and using a single `openLink` for every later same-process scene transition (`list.scroll`, `nav.transitions`), which needs no re-recovery since the JS engine and native view hierarchy are already warm. Confirmed post-fix: 10/10 clean Android cold-start runs of the real flow file, 6/6 clean iOS cold-start runs, then the 50/50 iOS run above.
- [x] Same YAML file drives both platforms (platform conditionals only in launch/app-id stanzas). Evidence: `flows/e2e.yaml` has a single `appId: com.emubench.rig` header and zero `platform:` conditionals anywhere in its command list (grep confirms no per-platform branching) — `maestro --udid <ios-udid> test flows/e2e.yaml` and `maestro -p android test flows/e2e.yaml` both run the identical file end to end (verified directly, repeatedly, against `bench-iphone` and `bench-tuned`).
- [x] Flake classification distinguishes retry-passes from real failures; both appear in results. Evidence: `src/scenarios/e2e.js`'s `e2e.flake_rate` classifies every failed original attempt with an immediate retry under the same cold-launch precondition — a retry that passes increments `flakeCount` ("fail-flake"), a retry that also fails increments `realFailCount` ("fail-real") — and logs both counts distinctly, e.g. the 50-run evidence line above names all three buckets (`50/50 pass, 0/50 fail-flake ..., 0/50 fail-real ...`) even though this run's actual counts were all in the pass bucket; the classification code path for a genuine fail-flake was exercised and confirmed correct during this ticket's own diagnosis work (the pre-fix Android runs produced real fail-flake/fail-real splits before the flow bugs above were fixed, visible in `e2e.duration leg b: 7/10 run(s) failed` — a distinct, separate benchmark not currently exposed to reclassification since `e2e.duration` doesn't retry by design, per its own module doc: samples are timed pass-or-fail, only `e2e.flake_rate` retries and classifies).
- [x] `--groups 6` includes both benchmarks; 50-run mode is behind a flag (`--flake-runs 50`) since it's slow. Evidence: `./bin/emu-bench run --groups 6 --label e2e --flake-runs 10` → `emu-bench: wrote /Users/tylerwilliams/emu-bench/results/apple-m3-max-2026-09-03-e2e.json`, containing both `e2e.duration` (legs b/c, n=8, medians 40.03s/36.83s) and `e2e.flake_rate` (legs b/c, n=8, `10/10 pass` both legs, 0% flake) rows alongside T10's existing Group 6 entries, with only one unrelated pre-existing skip (`refresh.metro` leg b, a transient marker-file timeout — T10's own scenario, out of this ticket's scope). `--flake-runs` defaults to a modest 10 (`src/scenarios/e2e.js`'s `DEFAULT_FLAKE_RUNS`, matching this ticket's own verification command) when the flag is omitted, so a plain `--groups 6` never silently pays for the full ~50-run/leg sweep (at this flow's observed ~35-40s/run, over an hour across both legs); the full "50 executions per platform" scope is reached only by explicitly passing `--flake-runs 50`, gating the slow mode behind the flag as criterion 4 requires. `ctx.flakeRuns` (threaded from `src/commands/run.js`'s `--flake-runs` flag) overrides the default when present — confirmed both at `10` (the command above, using the now-default value explicitly) and at `50` (the box-1 evidence run, which opted into the full mode).

## Risks

Maestro's Android and iOS drivers differ in tap/wait semantics; keep assertions on stable testIDs with generous-but-equal timeouts so the flow measures the environment, not driver timing quirks.
