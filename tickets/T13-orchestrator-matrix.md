# T13: Run orchestrator — matrix policy, hygiene enforcement, skip handling

**Blocks:** T14

## Context

`emu-bench run` turns the registry into a disciplined collection session (SPEC.md §5, §12; PLAN.md §5 controls). Two policies come from plan review and must be code, not documentation: the config policy (PLAN.md §5, SPEC.md §5 `run`) — tuned config primary for everything, with the **headline subset** — cold boot, `list.scroll` p95, `sqlite.insert_fsync`, `install.rig` — re-run on the default AVD — and the hygiene rules (interleaved legs, warmup discards, cooldowns, CV flagging, battery/thermal gates).

## Scope

- Full `run` implementation: consume `doctor --json`, boot/shutdown devices per leg as needed (tuned vs default AVD per config), execute registry benchmarks in **interleaved leg order** (A,B,C,A,B,C…) within each group, enforce per-benchmark n (≥10 macro / ≥30 micro, from registry metadata), discard 2 warmups, insert cooldown timers after GPU-heavy scenes (registry flag), compute stats, stamp CV flags.
- Default matrix = all available groups × legs, tuned; then the headline subset × leg B, default config. `--config tuned|default|both` overrides.
- Skip machinery: unavailable dependency, declined sudo, failed benchmark after one retry — all land in `skipped[]` with named reasons; the run continues.
- Session report: end-of-run console summary (per-group medians, flagged CVs, skips) and the results-file write with schema validation (refuse to write invalid).
- Resumability: `--resume <file>` continues an interrupted session (device crashed mid-run) without redoing completed benchmarks. Keep it simple — completed benchmark ids are skipped on resume.
- Runtime estimate printed up front (sum of registered durations) so a runner knows what they're committing to.

- [x] Interleaving verified in the run log (leg order alternates within groups). Evidence: run log and the results file's own row order both show, e.g. Group 1: `demo.noop_loop:a`, then `kernel.sha256:a,b,c`, `kernel.zlib_deflate:a,b,c`, `kernel.matmul_1024:a,b,c`, … — the A,B,C,A,B,C cycle repeats once per benchmark id within the group (src/commands/run.js `runPass`'s per-entry leg loop).
- [x] Killing the run mid-way and `--resume`ing produces a complete, valid file without re-running finished benchmarks. **Superseded evidence note:** the first pass at this box cited resuming from an already-*complete* rehearsal file, which only demonstrated the completed-key dedupe, not genuine interruption recovery, and separately never exercised what happens when a resumed cell had actually landed in `skipped[]` rather than `benchmarks[]` — both flagged correctly on review. Two bugs fixed:
  - **No checkpoint write existed.** The results object was assembled/validated/written exactly once, after every pass finished, so a real kill left no file at all. Fixed: `runPass` now checkpoints (validates + writes) after every single benchmark cell's outcome, not just at group/run boundaries — group-boundary-only checkpointing was tried first and directly falsified by this same testing (a `--groups 1` run SIGKILLed partway through Group 1 left zero files, since Group 1 alone runs long enough that no group boundary was ever crossed).
  - **Resumed skips went stale.** A carried-over `skipped[]` entry for a cell this run re-attempts was never cleared before the re-attempt (skips are deliberately excluded from `completed`), so a re-attempt that failed again appended a duplicate skip, and one that succeeded left a stale skip contradicting the new row. Fixed with `removeOneStaleSkip` (FIFO per `id`+`leg`, not a blanket removal — schema/v1.json's skip rows carry no `config` field, so the headline-subset ids attempted under both `tuned` and `default` on leg b can legitimately hold two independent same-id/leg skips; FIFO-consuming in the same tuned-then-default pass order the orchestrator itself uses keeps each config's re-attempt matched to the skip it actually made stale), called immediately before every cell's (re-)attempt in `runPass`.
    **Correction (post-review):** as first written, that fix was itself broken — "called immediately before every cell's (re-)attempt" searched the *entire* shared `skipped[]`, not just genuine resume-file carryover, so on a fresh (non-`--resume`) `--config both` run it could erase a skip *this same process* had just recorded on the tuned pass when the default headline pass later attempted the identical id+leg (silently vanishing that cell, or duplicating an independent failure as one) — the three re-verification scenarios below happened not to trip this because their skips were non-headline ids never attempted under a second config. Fixed by scoping eligibility to a `carriedSkips` count snapshotted once at load time (`skipped.length` right after `--resume` loads the prior file, 0 on a fresh run) and decremented on each successful removal; `removeOneStaleSkip` now only searches that carried prefix (new skips always `push` to the tail, so the prefix invariant holds for the run's whole lifetime), making it an unconditional no-op on a fresh run rather than incidentally-usually-safe.

  Re-verified for real, three scenarios: **(1) genuine crash recovery** — started `./bin/emu-bench run --groups 1 --label checkpoint-test`; confirmed `results/apple-m3-max-2026-09-03-checkpoint-test.json` appeared and validated after the very first benchmark (`demo.noop_loop`); let it reach 3 recorded benchmarks (`demo.noop_loop:a`, `kernel.sha256:a`, `kernel.sha256:b`) with a 4th (`kernel.sha256:c`) in flight, then `kill -9`'d the orchestrator process outright (not a graceful stop) to simulate a real crash; the on-disk file was schema-valid with exactly those 3 rows and the in-flight 4th correctly absent. Resumed with `./bin/emu-bench run --groups 1 --resume <that file>`; log showed the 3 completed cells skipped and `kernel.sha256:c` (the lost in-flight one) re-run first, then every remaining Group-1 kernel; the run finished on its own to a schema-valid file with all 25 Group-1 benchmark/leg rows, 0 skips, 0 duplicate cells. **(2) stale skip cleared on a successful re-attempt** — built a synthetic scratch file from that same checkpoint with `kernel.getpid_loop:a:tuned`'s benchmark row removed and a fabricated stale `skipped[]` entry injected for that exact cell (independently schema-valid before use); `--resume`d with `--groups 1`; log showed only that one cell re-run (every other cell already re-verified as completed), it passed, and the final file has `Skips: 0` with a fresh `kernel.getpid_loop (leg a, tuned)` row — the injected skip is gone, not left dangling beside the new row. **(3) no duplicate when a re-attempt fails again** — a minimal synthetic file with only a stale `skipped[]` entry for `photon.latency:b` (a real, reproducible failure in this environment — the Screen Recording TCC gap noted in the box above); `--resume`d with `--groups 4`; `photon.latency` leg b genuinely failed its retry again, and the final file's `skipped[]` contains exactly **one** `photon.latency`/leg-b entry carrying the fresh failure's real reason, not the fabricated text — no duplicate.
