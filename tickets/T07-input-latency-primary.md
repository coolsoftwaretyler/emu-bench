# T07: Input latency, primary — in-app touch→frame scene + tap driver (Group 4)

**Status:** done (2026-08-30)
**Depends on:** T04 (harness), T06 (frame recorder conventions)
**Blocks:** T09 (shares the tap flow), T13

## Context

PLAN.md Group 4's primary input-to-photon metric: measured **inside the app** — touch-event native timestamp → next presented frame after the resulting state change commits — with identical JS on both platforms, so the injection tool's own latency cancels out of the comparison (it only needs to deliver taps, not deliver them fast). Hypothesis H6.

## Scope

- `touch.latency` scene: full-screen touchable; on press, read the event's native timestamp (`event.nativeEvent.timestamp` — verify its clock domain per platform and normalize; document the normalization in the scene source), trigger a visible state change, record delta to the next frame-present callback. Collect ≥ 30 taps; emit samples + median/p95 via the standard contract. Visual feedback must be an obvious high-contrast change (T09 reuses it for pixel-diff detection).
- Tap driver: Maestro flow (`flows/touch-latency.yaml`) tapping the scene N times at ~1 s intervals, shared YAML with per-platform launch stanzas. Fallback driver via `adb shell input tap` for Android if Maestro's tap cadence proves unreliable — but Maestro must remain the documented default so both platforms use the same injector.
- Registry entry: `--groups 4` runs the scene by launching it, executing the flow, then extracting results.

## Acceptance criteria

- [x] ≥ 30 valid tap samples per run on both platforms; taps that miss (no state change) are excluded and counted in the results `notes`. Evidence: `./bin/emu-bench run --groups 4 --label touch-primary` (both devices booted: `emulator-5554`, `bench-iphone` simulator) wrote `results/apple-m3-max-2026-08-30-touch-primary.json` with `benchmarks[]` n=30 on both leg b and leg c (32 taps collected by the Maestro flow, 2 discarded as orchestrator warmups per `run.js`'s standard `WARMUP_DISCARDS=2` — same convention as every other scene), `skipped: []`. Miss-counting verified by code path: `TouchLatencyScene.tsx`'s `missTimerRef` (2000ms timeout) increments `missCountRef` and the scene reports `missedTaps`/`notes` (`"No missed taps."` when zero, else a count + reason) in its own measurement payload per SPEC §9's scene-JSON contract; `rig-scenes.js`'s registry entry logs to console when `missedTaps > 0`. All three verification runs in this ticket showed 0 missed taps.
- [x] Clock-domain handling verified: deltas are plausible (2–100 ms range, not negative, not seconds) on both platforms. Evidence: Android's `nativeEvent.timestamp` traced to RN's `TouchEvent.kt`→`MotionEvent.eventTime` (`SystemClock.uptimeMillis()`); iOS's traced to `RCTTouchHandler.m`→`UITouch.timestamp*1000` (mach-uptime-derived) — see `TouchLatencyScene.tsx`'s file-doc for the full trace. Neither shares an epoch with `performance.now()`, so the scene bridges via a **running-minimum offset** refined across every tap in a run (`offset_i = performance.now() - nativeEvent.timestamp` at press time; true offset is upper-bounded by every observed `offset_i` since each tap's responder-dispatch delay is ≥0, so the minimum is the best estimate) — a single-tap calibration was tried first and produced negative deltas on iOS during development (e.g. -7ms, -12ms, -13ms on an early 4-tap manual test), diagnosed as the first tap's own dispatch-delay noise being baked permanently into a fixed offset; switching to a running minimum recomputed once at run-end fixed it (verified: 8/8 samples positive and 15-30ms range on the very next iOS run). Final `touch-primary` run: leg b (emulator) samples span 0.59-17.12ms (28/30 within the stated 2-100ms band; 2 samples at 0.59ms/1.49ms sit modestly below the 2ms floor — plausible given Maestro's synthetic UI-Automator tap injection rather than a real finger, not a clock-domain defect: no negative or seconds-scale values anywhere, and the scene's `clockOffsetMs`/`firstTapCalibrationMs` diagnostic fields are small and sane in every run); leg c (simulator) samples span 15.81-32.19ms, entirely within 2-100ms. All non-negative, all sub-second, on both platforms across all 3 runs performed.
- [x] Repeatability: two consecutive runs on the simulator differ by < 20% at p50. Evidence: `./bin/emu-bench run --groups 4 --label touch-repeat-1` then `--label touch-repeat-2`, leg c (simulator) medians 22.140ms vs 22.741ms — 2.7% delta, well within the 20% gate. (Leg b/emulator also checked: 9.641ms vs 8.922ms, 7.5% delta.)
- [x] End-to-end via CLI with both devices booted. Evidence: all three runs above (`touch-primary`, `touch-repeat-1`, `touch-repeat-2`) executed `./bin/emu-bench run --groups 4` with `emulator-5554` and the `bench-iphone` iOS simulator both already booted; each wrote a schema-valid results file (`validateAgainstV1()` re-run directly against `touch-primary`'s file returned `valid: true`, 0 errors) with 2 `benchmarks[]` entries (legs b, c) and 0 `skipped`.

## Verification

```bash
./bin/emu-bench run --groups 4 --label touch-primary
```

Compare medians across legs; direction should show emulator ≥ simulator. If emulator < simulator, suspect timestamp clock domains before celebrating.

**Spot-check evidence (2026-08-30):** `touch-primary`'s medians show **leg b (emulator) 7.10ms < leg c (simulator) 20.88ms — the opposite of the predicted direction**, consistently reproduced across all 3 verification runs (repeat-1: 9.64 vs 22.14ms; repeat-2: 8.92 vs 22.74ms — emulator lower every time, never close). Investigated per this section's own instruction before accepting the result: the clock-domain bridging was independently verified correct on both platforms (traced both platforms' native timestamp source in RN's own source, confirmed the running-minimum-offset fix eliminates the negative-delta failure mode entirely — see acceptance criterion 2's evidence), and every sample on both legs is positive, sub-second, and mostly within the stated 2-100ms band, so this is not a clock-domain artifact reproducing PLAN.md's predicted direction backwards. Recorded here as an honest finding rather than forced to match the prediction: plausible explanation is that Maestro's `tapOn` on Android delivers a synthetic UI-Automator touch event, and `MotionEvent.eventTime` for an injected (non-hardware) event may be timestamped at injection/dispatch time rather than at a genuine hardware-interrupt time the way a real finger-touch would be — i.e. Android's native timestamp may already be closer to "when Android's input pipeline handed the event to the app" than iOS's simulator-injected `UITouch.timestamp` is, understating the guest↔host/VM-boundary latency this metric is meant to expose for *real* touches. This is a genuine limitation of using an automation-injected tap (both here and in Group 4's Fence round-trip/T08) rather than the scene's own instrumentation being wrong — worth a closer look by whoever next interprets Group 4 data, same spirit as T06's own S2-fillrate direction caveat.

**Maestro `openLink` routing bug, diagnosed and worked around (documented in `flows/touch-latency.yaml`):** `launchApp` immediately followed by a single `openLink` reliably failed to route the app to the target scene on *both* platforms (confirmed via Maestro's own captured accessibility-hierarchy debug output showing the debug scene-list screen's text at the failure point, not `touch.latency`'s — ruling out a stale-snapshot false negative). Ruled out as a timing race (tested up to a 30s post-`openLink` wait) and as simulator/daemon staleness (reproduced identically after a full `xcrun simctl shutdown`+`boot`). A second, immediate `openLink` call reliably recovers on both platforms (verified across 5+ repeated manual runs plus all 3 full verification runs) — this workaround is now baked into the flow file with the diagnostic trail recorded in its comment header. `tapOn` itself was never unreliable once the correct scene was genuinely showing (proven via an isolated tap-only flow against a manually-pre-launched scene: 8/8 real Maestro-injected taps succeeded on Android). No fallback driver was needed for either scene-routing or tap-delivery in the end — Maestro remains the sole driver end to end on both legs, per this ticket's own preference ("Maestro must remain the documented default").

## Risks

`nativeEvent.timestamp` clock domain differs across platforms/RN versions (uptime vs epoch). Budget time to verify against `performance.now()` bridging on each platform; record the method in the scene source and results `notes`.
