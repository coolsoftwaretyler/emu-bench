## Context

The end-to-end variant of input latency: records the **Mac screen** (not the device framebuffer) while taps are injected, so the measurement includes the emulator/simulator window compositor path that T07's in-app metric can't see (PLAN.md Group 4, SPEC.md §10). Explicitly secondary in all reporting because injection paths differ per platform; n≥30 to survive the ±1 frame quantization at 60 fps capture.

## Scope

- Capture: `ffmpeg -f avfoundation` screen recording at 60 fps, started/stopped by the scenario script; device window region located automatically if cheap (window bounds via `osascript`/CoreGraphics window list) or via a one-time calibration step that saves the region to the run config.
- Tap marking: reuse T07's `touch.latency` scene; the tap must be visually detectable in the recording — either the scene's high-contrast response alone (count frames from injected-tap timestamp logged by the driver to first pixel change), or better, a cursor-position flash marker if timestamp alignment proves unreliable. Choose one method, document it, record it in provenance as `method`.
- Frame-diff analyzer: script (node, zero deps — decode via ffmpeg to raw frames piped in) that finds the first frame where the device-window region changes beyond a threshold after each tap; emits per-tap latency in frames and ms.
- Registry entry `photon.latency`, group 4, legs b/c only (no leg-A analog); auto-skip with a named reason when ffmpeg is absent.

## Risks

Screen-recording permission (macOS TCC) must be granted to the terminal — doctor should detect a black recording and print the System Settings instruction. Window-region detection is the fiddly part; a manual `--region x,y,w,h` escape hatch is acceptable for v1.

**Implementation note on black-recording detection:** lands in `src/photon.js`'s `looksLikeBlackRecording()` (checked immediately after each leg's own capture, before analysis) rather than in `src/commands/doctor.js` — `doctor` runs once, before any device is booted or any scene is on screen, so it has nothing real to record and test blackness against at that point; the check only makes sense against an actual capture attempt, which only happens during `run`. Verified directly: a genuinely all-black synthetic recording (`ffmpeg`'s `blackdetect=d=0.5:pic_th=0.98` filter) measured 99.4% black-duration ratio; a realistic 50/50-alternating recording (matching `touch.latency`'s COLOR_DARK/COLOR_LIGHT flip cadence) measured exactly 50% — comfortably below the 90% threshold this function uses, so the check has a wide, verified margin between the true-failure and normal-operation cases. When it fires, the thrown error names the System Settings path exactly as this Risk anticipates ("Grant it in System Settings > Privacy & Security > Screen Recording, then re-run") and lands in `skipped[]` with that reason, same as every other failure mode this module can hit. Live-triggered during this ticket's own earliest (pre-permission) leg-b verification run (see acceptance criterion 1) — though in that run, the screen-capture-device lookup (checked before any recording is even attempted; since renamed/replaced by `resolveCaptureDeviceForRegion()`) fired first, since no `Capture screen` device is listed at all without the permission — `looksLikeBlackRecording` is the fallback layer for the rarer case where a screen device exists but records black anyway (e.g. permission revoked mid-session, or granted to the wrong app in a multi-terminal setup).
