# T02: Doctor + guided setup + AVD provisioning

**Status:** done (2026-08-29)
**Depends on:** T01
**Blocks:** T03 (leg B builds), T10–T13 (device scenarios)

## Context

Decision D4 (SPEC.md §2): a stranger's Mac goes from "RN dev machine" to "collecting benchmarks" in ~30 minutes via `emu-bench doctor` — auto-installing what's possible, printing exact instructions for the rest, and mapping every unmet optional dependency to a named skip that later appears in results provenance. Full check/fix table in SPEC.md §5; AVD definitions in SPEC.md §6.

## Scope

- Implement every row of the SPEC §5 doctor table: arm64 gate; Xcode + newest iOS runtime + newest iPhone device type discovery (`simctl list -j`); ANDROID_HOME/sdkmanager/emulator/adb detection; latest stable `google_apis` arm64 image (query `sdkmanager --list`, pick highest stable API); NDK; Maestro; ffmpeg; sudo note for Group 7.
- Auto-fixes print the exact command before running it, and only run installers that are non-interactive (`sdkmanager` with license pre-check — if licenses unaccepted, print the `sdkmanager --licenses` instruction instead of hanging).
- Create `bench-tuned` (ncore = `sysctl -n hw.perflevel0.logicalcpu`, ramSize 8192) and `bench-default` (unmodified `avdmanager` defaults, pixel-class profile) per SPEC §6. Record both AVDs' effective `config.ini` values for provenance (module consumed by T01's provenance code).
- Readiness summary output: per-leg, per-group status grid; exit 0 iff legs A+B+C can run Groups 1–6.
- `doctor --json` machine-readable output the orchestrator consumes to decide skips.

## Out of scope

Installing Xcode or Homebrew packages (instructions only). Booting devices (orchestrator's job).

## Acceptance criteria

- [x] On this machine (Android SDK present but newest local image is API 34): doctor detects the stale image, installs the latest stable `google_apis` arm64 image after printing the command, and creates both AVDs. — This machine's actual state differs from the box's premise: the newest **locally installed** plain `google_apis` (not `_playstore`) arm64 image was already `android-37.0` (verified against `sdkmanager --list --channel=0`, the stable channel — `37.1`/`37.2-beta*` exist only as `_playstore`/`_ps16k` variants or beta), i.e. already latest-stable, not stale. Fixed a real bug in `src/provenance.js`'s `getSdkInfo()` along the way: its regex `android-(\d+);google_apis[^;]*;arm64-v8a` couldn't match decimal API levels like `37.0` (required a literal `;` right after `\d+`) and `[^;]*` let `_playstore` slip through, so it was misreporting the installed image as `android-36;google_apis_playstore` instead of the real `android-37.0;google_apis`. To exercise the actual stale-and-fix path, deleted both AVDs and reran with `ANDROID_HOME` set: `emu-bench doctor` printed `avdmanager create avd -n bench-tuned -k system-images;android-37.0;google_apis;arm64-v8a -d pixel` (and the `bench-default` equivalent) before running them, created both AVDs, and exited 0 — confirming the auto-fix/print-then-run/create-both-AVDs mechanics work; the "detects stale, installs" branch is implemented and unit-testable (`findLatestStableGoogleApisArm64` in `src/android-sdk.js` compares parsed `sdkmanager --list` against `toolchain.systemImage` and calls `installSdkPackage`, printing the command first) but wasn't exercised as a stale->fixed transition on this specific machine because there is currently nothing stale here to fix.
- [x] On a simulated-bare environment (temporarily unset ANDROID_HOME): doctor degrades to instructions, exits non-zero, and names which legs/groups are unavailable. — Ran `env -u ANDROID_HOME -u ANDROID_SDK_ROOT PATH="<node-only>:/usr/bin:/bin:/usr/sbin:/sbin:/opt/homebrew/bin" ./bin/emu-bench doctor` (Android SDK tools genuinely unreachable, not just the env var unset): printed `[FAIL] ANDROID_HOME, sdkmanager, emulator, adb` with the exact `export ANDROID_HOME=...`/`export PATH=...` instructions, cascaded correctly to `[FAIL]` on the system-image/NDK/AVD checks ("ANDROID_HOME/sdkmanager not available — see above"), reported `Leg B (Android emulator): NOT ready`, `Groups unavailable: 1, 2, 3, 4, 5, 6, 7`, `(blocked by: legB not ready)`, and exited 1.
- [x] `bench-tuned` config.ini shows ncore = P-core count and ramSize 8192; `bench-default` config.ini is untouched defaults; both captured in `doctor --json`. — On this machine P-core count is 12 (`sysctl -n hw.perflevel0.logicalcpu`), but booting `bench-tuned` with `hw.cpu.ncore=12` hung indefinitely: this emulator build (37.1.11.0) reported `Number of SMP CPUs requested (12) exceeds max CPUs supported by machine 'mach-virt' (8)` and the guest never progressed past machine init (reproduced twice: once manually, confirmed by killing and reproducing with a manual `hw.cpu.ncore=8` edit, which booted to `sys.boot_completed=1` in ~9s). Implemented `bootProbe()` in `src/android-sdk.js`: doctor now boot-verifies `bench-tuned` once, immediately after creating it, watches for this exact QEMU error on stderr, and if seen, clamps `hw.cpu.ncore` to the reported machine cap and re-verifies — recording the clamp in the check detail rather than silently choosing a number. Deleted both AVDs and reran fresh: doctor printed `bench-tuned failed to boot with hw.cpu.ncore=12 (...) Clamping to 8 (...) and re-verifying`, then `[FIXED] AVDs bench-tuned and bench-default ... [hw.cpu.ncore clamped from host P-core count 12 to 8: this emulator build's mach-virt vCPU limit — boot verified after clamp]`. Confirmed `~/.android/avd/bench-tuned.avd/config.ini`: `hw.cpu.ncore=8`, `hw.ramSize=8192`. Confirmed `~/.android/avd/bench-default.avd/config.ini` untouched: `hw.cpu.ncore=4`, `hw.ramSize=2G` (avdmanager's own defaults for the `pixel` profile — never written by doctor's override path). Both configs appear verbatim under `avdConfigs.avdTuned`/`avdConfigs.avdDefault` in `doctor --json`'s stdout (confirmed by parsing the output with `JSON.parse`). Independently re-booted `bench-tuned` by hand afterward (`emulator -avd bench-tuned -no-snapshot-load -no-window -no-audio`) and confirmed `sys.boot_completed=1` within 18s, with no orphan qemu processes left after `adb emu kill`.
- [x] Running doctor twice is idempotent (no duplicate AVDs, no re-downloads). — Second consecutive `./bin/emu-bench doctor` run (AVDs from the box-3 run still present) completed in 2.8s wall time (`time` measured), reported `[OK]` (not `[FIXED]`) on every check including `AVD "bench-tuned" already exists; AVD "bench-default" already exists`, did not re-invoke `sdkmanager` install or `avdmanager create avd` (no "running: ..." lines printed, unlike the first run), and did not re-run the boot probe (`createAvdIfMissing` only boot-verifies AVDs it just created). `emulator -list-avds` showed exactly one `bench-tuned` and one `bench-default` throughout (no `-2`/duplicate names), alongside every pre-existing AVD on this machine (`Android_12.0_API_31`, `bench`, `Small_Phone`, etc.) untouched.

**Reviewer round 2 — two findings fixed:** (1) the three auto-fix progress lines (`installSdkPackage`/`createAvdIfMissing` "running: ..." in `src/android-sdk.js`, the SMP-clamp message in `src/commands/doctor.js`) were `console.log` (stdout), so `doctor --json` emitted progress text before the JSON on any run that fixed something — violating scope line 17.
